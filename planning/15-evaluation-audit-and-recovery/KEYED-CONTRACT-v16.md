# Prospective keyed contract campaign v16

The successor replaces repeated identity rows with required named keys, then derives claim/part identifiers and checker digests from the exact sealed/current context. Scientific acceptance, selected-source identity, whole-claim support, atomicity, four qualification judgments, request coverage, priority and every prose finding remain mandatory. Learn permits up to eight claims and Research up to twelve; nullable required claim slots permit fewer. A keyed schema is not evidence of provider grammar acceptance or complete output.

The existing v15 capacity policy, model routes, deadlines and programme ceilings remain unchanged: 64 programme jobs, 160 Messages, 200 counts, USD20, concurrency one, programme expiry 2026-11-21T11:03:57Z. The separate prospective campaign has 14 identities in the predecessor order, at most 44 Messages and 44 paired counts, USD14 new spend, and expiry at most 24 hours after approval and never later than programme expiry. Both historical uncertain-contact holds remain preserved without settlement. No programme renewal or cap amendment is requested.

The v16 extension appends a distinct extension ID in the additive revision-8 keyed continuation table (migration021); its predecessor foreign keys reference the immutable v15 capacity receipt. It verifies the stopped v15 parent receipt independently of current producer hashes. Migration021 creates separate append-only continuation/revocation tables and changes none of migrations001–020. Its future live application requires explicit migration approval. Templates remain unapproved; recording requires a new exact owner receipt. Fixture authorizations require marked offline storage and the disabled credential. Packet freezing is permitted only in marked fixture storage. The fixture census copies public data and financial/authorization records, excluding owner notes/history.

The normal draft/check/repair/check workflow retains its single quality repair. A completed but schema/semantic-invalid draft remains a terminal contract rejection. Enabling a future draft/repair/check branch requires a separately bound journal contract, preserved rejected-draft diagnostics, and independent mandatory final checking; this revision does not add that branch.

Validation: immutable archived parent and four negative controls (changed receipt, active parent scope, changed programme expiry, revocation); exact predecessor packet digest; Python syntax and Ruff. Integrated fixture freeze/run/report and Reader checks must be performed against the composed new draft/checker/runtime source, then archived separately. No provider/count contact, live ledger mutation, owner listener write, PR, push, merge or deployment is part of these checks.

## Contract compatibility audit

This prospective revision changes generated representation, not retrieval,
reference labels, scoring thresholds or historical interpretation. Original
v3–v15 outputs, failed scopes, source packets, scores, financial receipts and
both historical holds remain under their original identities.

| Rejection or invariant | Wire enforcement, safe derivation, or required semantic validation |
|---|---|
| Every requested part exactly once | Required named `coverage.p1`… properties, no `part_id` field or row groups; closed objects reject unknown parts; strict raw JSON parser rejects duplicate keys before normalization. |
| Several missing details for one part | One `gap_reasons` collection on that part; evidence and omission reason vocabularies remain separate. All reasons, their order, context links and rendered text survive storage and export. Repeated identical reason codes remain a local error. |
| Status and answer/context roles | Shared status-specific value definitions; fixed enums survive SDK transformation. Answers require answer references and `none`; evidence gaps and omissions forbid answer references. Duplicate/overlapping references and their existence remain cross-reference checks. |
| Full abstention | Its branch has no claims or claim references. Missing application context seals that branch and required context fields before drafting. No self-selected comparison-only or null reason can change that application policy. |
| Comparison-only abstention | Its branch forbids comparison/basis claims and answered comparison parts; separately cited source notes remain allowed. Two actual source bases and whole-comparison support still require semantic validation. |
| Generated claim identities | Required mode-specific named slots `c1`…`c8` or `c12`, with `c1` populated and unused later slots null. The server derives IDs from keys; a second `claim_id` or `part_ids` mapping is forbidden. Null-slot references and orphan claims remain errors. |
| Expanded references | Section, question and coverage reference enums use the actual 8/12 mode cap. Actual referenced claims must exist; duplicate references, overlap and source/basis relationships remain checked locally. |
| Question premises | Neutral intent values are rendered locally. The cited-claim question branch requires nonempty emitted-claim references on the wire; validity and whole-premise support remain checked. |

The checker supplies decisions, not IDs or input digests; the server derives those from the exact sealed checker request after strict parsing and shape validation. Each contains an array of independent reasons; multiple reasons at one location survive. The server derives field/index; unknown locations and exact duplicate findings are rejected. Expanded assumption indices are not limited by the old three-question index bound. |
| Evidence identity | Selected handle enums prevent source expansion. Server-owned material/version/parser/hash/quote/Unicode offsets remain validated. A resolving citation never establishes whole-claim support. |
| Mandatory quality | Support, atomicity, all four qualifications, requested-part coverage, priority and prose judgments remain mandatory. Unsupported, uncertain, bundled or lost-qualification findings still block acceptance under unchanged rules. |
| Complete response and capacity | Expected model, complete `end_turn`, strict finite JSON, role-specific raw/normalized/HTTP byte guards, measured input fit and output-token limits remain independent. No prefix salvage, explanation truncation or missing-verdict default is allowed. |
| Current-response assessments | Exact journal order, complete raw response, paired count, reconstructed request/schema/settings, entire current response and a completed checker after its latest repair remain bound. An uncertain or absent recheck leaves judgments unavailable. |

Reader downloads whitelist the complete result and exact references; notes exceeding the existing body limit save an explicit exact-job reference instead of truncating the result. |

### Repair eligibility

A valid draft followed by a complete negative quality check can consume the
existing single repair, followed by mandatory recheck. Rejected first-draft
contracts remain terminal in this revision. Safely supporting a different
`draft → rejected-draft diagnostic → repair → check` sequence would require a
separately sealed journal branch, strict metering and parsing eligibility,
repair-consumption state and corresponding report reconstruction. Catching a
validation error and pretending a checker existed would violate current-response
bindings. This batch does not add that shortcut or reopen any stopped job.

### Archived failure controls

The offline controls retain the observed classes separately: evidence-handle
versus claim-ID confusion; factual prose outside scored claims; lost source
hedges; over-restrictive ordinary prose; procedural questions with factual
premises; answer/evidence-gap shape conflict; competing claim-to-part mappings;
uncertain timeout; truncated or `max_tokens` checker output; provider grammar
HTTP400; and duplicate requested-part rows. Original failures stay failed. A
converted example is explicitly synthetic and receives neither provider-success
nor factual-support credit. Matching historical source text or a valid quotation
alone cannot pass the factual gate.

### Verification boundaries

Schema size and shared definitions are reported, not treated as proof of remote
compiled-grammar acceptance. Mock counts are software fixtures, never measured
token fit. New actual requests need exact paired counts under a future single
campaign approval; there is no separate preliminary count-only stage. Browser
screenshots with synthetic API fixtures establish rendering/interaction only;
real isolated Postgres tests establish persistence separately. Human labels
remain blank and checker qualification remains disabled.
